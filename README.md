# Skills Viewer 1.0

A local desktop/browser dashboard for discovering, inspecting, editing, and reusing AI agent skills. No cloud, account, Electron shell, package dependencies, database, or background watcher.

## Desktop application

The self-contained version **1.0.0** archives in `dist/` include a checksum-verified Node.js 22 LTS runtime. No separate Node install is needed for these packages.

| Platform | Archive | Start |
| --- | --- | --- |
| macOS Apple Silicon | `skills-viewer-1.0.0-darwin-arm64.zip` | Extract and open **Skills Viewer.app**. |
| macOS Intel | `skills-viewer-1.0.0-darwin-x64.zip` | Extract and open **Skills Viewer.app**. |
| Linux x64 | `skills-viewer-1.0.0-linux-x64.tar.gz` | Extract and run `./skills-viewer/skills-viewer`. |
| Linux ARM64 | `skills-viewer-1.0.0-linux-arm64.tar.gz` | Extract and run `./skills-viewer/skills-viewer`. |

Every click on the application icon opens your default browser with a private access link. The short-lived desktop launcher starts a background loopback server on an available port, or reuses the running desktop server for that profile. The app uses your browser instead of embedding another Chromium instance. **Stop app** in the footer shuts down the server; closing the tab alone does not. Click the icon again to reopen the dashboard or restart it after stopping.

macOS builds are **unsigned and not notarized**; a downloaded app may require macOS's explicit “Open Anyway” approval. They require macOS 11 or newer. Linux requires a desktop session with `xdg-open` and a compatible glibc-based distribution (glibc 2.28+); these are not Alpine/musl builds. Native execution is verified on the build Mac; do not assume an unexecuted target has been runtime-tested.

On Linux, run `./skills-viewer/skills-viewer --install` once after extraction to add **Skills Viewer** to your application menu with absolute executable and icon paths (no PATH changes needed). Then click its icon to open the browser. Keep the extracted folder in place with its bundled `runtime/` and `app/`; rerun `--install` if you move it. Desktop launch diagnostics are in `~/.config/skills-viewer/launcher.log` (or `SKILLS_VIEWER_DATA_DIR/launcher.log`).

Rebuild all four archives, or pass specific targets:

```sh
npm run package
npm run package -- darwin-arm64 linux-x64
```

Packaging downloads only public Node.js binaries and their official SHA-256 manifest from nodejs.org; the running app itself never needs the network. The package builder copies a fixed source allowlist, not your workspace or profile. `dist/SHA256SUMS.txt` covers the archives generated by the latest packaging invocation. Bundled runtime licensing is included.

## Run

Requires Node.js 22 or newer.

For an existing checkout, open a terminal in the application folder. For a fresh private clone, first run `git clone YOUR_PRIVATE_REPOSITORY_URL` and `cd skills-viewer` (replace the URL with the repository's clone URL; GitHub authentication is required).

```sh
node --version
npm start
```

Open the **private launch URL printed in your terminal**, not just the bare localhost address. Its URL fragment carries a random per-process access secret. The page consumes that fragment and keeps the secret in tab-scoped sessionStorage. Every API endpoint, including reads, requires it; `/api/state` never returns it. Do not share the launch link. A plain `http://127.0.0.1:4317` can show the UI/FAQ but cannot read or modify skills without authorization.

No `npm install` is needed. Stop with Ctrl+C or **Stop app**. To use another port: `PORT=4320 npm start`. Restart the server after backend changes; its private link changes too. `npm run desktop` opens your browser automatically. Restarted/unauthorized tabs can paste the new private launch URL into the Connect form.

```sh
npm test
npm run check
```

## Pages and in-app help

The **Help & FAQ** page includes these explanations, folder examples, troubleshooting, and startup steps. The information icons and **About this page** disclosures link to the relevant answers.

| Page | Purpose |
| --- | --- |
| Library | Combined inventory of registered skill locations. Search, inspect, edit original instructions, share a link/copy, or remove one selected location. It is not a storage folder. |
| Agents | User-registered skills destinations and path-existence evidence. Add a name/path, optionally choosing a common path suggestion. Remove any registration, including the shared library. |
| Workspaces | Registered repositories or direct skill collections. Discover candidate repositories and explicitly register them. |
| Activity | Last 200 sharing/removal/restore events, managed-link disconnection, removal of inactive history entries, and pending recovery entries with Restore. |
| Help & FAQ | Definitions, link/copy behavior, detection rules, architecture, filesystem layout, privacy, and recovery rules. |

An **agent** is the named tool/destination. A **workspace** is a local project directory. A **skill** is a directory containing `SKILL.md` and optional supporting files. **System level** means this user's home-directory agent locations, not all operating-system accounts.

## What agent detection actually means

There is **no AI-based discovery**, executable lookup, package inspection, or process inspection. Register each agent using **Agents → Add agent**, its name, and its documented skills folder. Common suggestions autofill a path only after you select one and do not register anything until you save.

Fresh profiles contain only **Shared library** (`~/.agents/skills`), not an inferred agent list. **Registered agents** counts your registered destinations excluding the default shared library. Folder existence is not proof of installation or skill support.

A newly installed agent does not appear automatically. A removed registration stays removed across restarts. Upgrades preserve existing configured destinations; untouched personalized legacy placeholders with no skills path are dropped. Older registered destinations can all be removed, even if an older version called them “built-in.”

## Rescan versus Discover folders

**Rescan** is read-only. It rechecks registered sources, reads skill metadata, resolves directory symlinks, refreshes counts, and reports errors. It does not register new workspaces, copy/link files, execute scripts, or modify skills. Inventory reads also happen on page load and after changes. There is no background watcher.

**Discover folders** searches bounded common project locations for repositories with known skill paths and suggests candidates. Registration remains explicit. It does not discover unknown agent brands or recursively crawl the whole disk.

## Sharing a workspace skill with an agent

1. **Workspaces → Add workspace:** enter an absolute repository path. A folder containing skill directories also works. **Discover folders** can suggest other repositories.
2. **Agents → Add agent:** enter its name and the exact skills folder its documentation specifies. If an agent does not implement skills, creating a folder or link cannot add that capability.
3. **Library:** select a workspace skill, inspect the instructions and supporting filenames, then **Share with agents**.
4. Choose **Link to source** and one or more registered agents. The entire directory, including scripts and references, becomes accessible at the destination.

Links work independently of the dashboard. Close the dashboard/server when not in use. Agent reload behavior varies; start a new agent session or use its reload command if it caches skills.

## Discovery and sharing

- Suggested system locations: `~/.agents/skills`, `~/.claude/skills`, `~/.codex/skills`, `~/.copilot/skills`, `~/.cursor/skills`, and `~/.gemini/skills`. Only registered destinations are scanned, with Shared library registered initially.
- Workspace locations: `.agents/skills`, `.github/skills`, `.claude/skills`, `.codex/skills`, `.copilot/skills`, `.cursor/skills`, `.gemini/skills`, or a directly registered folder containing skill directories. Each skill is a directory containing a regular `SKILL.md`.
- Source-mode startup initially registers the current working directory; desktop mode starts with no workspaces. Other repositories require registration. Discovery searches common `Projects`, `AI Projects`, `Developer`, `code`, `repos`, `work`, and `git` folders and the current project's parent, up to three levels and 1,500 directories, without registering candidates silently.
- Skills linked to the same real directory appear once, with all discovered locations. Independent copies appear separately.
- **Link:** no duplicated files; changes to the source affect all links. Moving/deleting the source breaks its links. Agents must support directory symlinks.
- **Copy:** independent snapshot of the full directory. Future edits do not propagate. Copies containing symbolic links or special files are rejected; copies are capped at 25 MiB and 2,000 files/folders.
- **Shared library** follows the `.agents/skills` convention. It is not automatically supported by every agent. For explicit access, share to each configured agent destination.
- Existing destinations are never overwritten, merged, or deleted. Conflicts and partial multi-agent failures are reported per destination.
- Editing `SKILL.md` changes the original source, not a local dashboard copy. Saves check for stale content and use atomic replacement; confirm before saving. This is not a replacement for version control, and simultaneous external writers are not locked out.
- **Activity → Disconnect link** removes only an unchanged symbolic link created by this application. Source files are never deleted. Copies are intentionally not auto-deleted.
- After disconnection the location disappears from the skill inspector, while its registered agent stays available to share again. **Remove entry** clears the inactive history record; it changes no skill files. Active links and pending recovery entries cannot be dismissed this way.
- Removing a registration forgets a source/destination only; it does not remove skills or existing links.
- Discovery is bounded at 6,000 candidate skill folders per inventory. `SKILL.md` preview/edit is capped at 512 KiB; inventory names/descriptions are shortened to 160/500 characters. Only a small metadata subset (name and description, including common folded/literal blocks) is parsed; the original Markdown is shown as escaped text, never executed or rendered as raw HTML.

## Remove and restore skills

1. Select the skill in **Library → Remove skill**.
2. Select the exact location and type the skill name to confirm.
3. A symbolic-link location moves only that link to recovery storage; its source stays untouched. An original/copy moves the entire directory, including supporting files.
4. Open **Activity → Removed skills → Restore** to restore the location.

Original sources with other registered locations cannot be removed until those links/registrations are removed. Links outside registered folders cannot be detected: check other consumers first. Removal refuses stale documents or changed locations. Restoring refuses occupied original paths, missing link targets, or a changed canonical parent/device/inode. A child process pins recovery writes to the verified original directory rather than following replaced ancestor symlinks. Legacy recovery records without parent identity require manual restoration after checking their original location.

Recovery storage is `<profile>/trash/<removal-id>/skill`, **not** the OS Trash. Moves are atomic and must stay on the same filesystem; cross-filesystem removal is refused without deleting or copying the source. There is no automatic expiry or permanent-delete action. Pending recovery records survive history trimming; empty recovery directories may remain after restoration. Recovery is not a version-control backup.

## Architecture and folder structure

In these paths, `~` means your home folder; names beginning with a dot are normally hidden folders on macOS/Linux. Workspace skill folders belong inside the relevant repository, not inside this dashboard's installation directory.

```text
Browser (HTML/CSS/JavaScript)
  -> local HTTP JSON API (server.mjs, 127.0.0.1)
  -> validated filesystem operations (core.mjs)
  -> registered skills + local settings/recovery storage
```

The browser cannot directly read the disk. The Node process operates with your user's permissions. **All API requests** require an owner-provided startup secret. Mutating requests are serialized. Run one server per profile; external writers are not globally locked out. Treat skill repositories as untrusted instructions, and review them before sharing.

```text
skills-viewer/
  package.json        Start, test, and syntax-check commands
  server.mjs          Loopback HTTP server, static assets, API routing
  launcher.mjs        Desktop/browser launcher and lifecycle
  recovery.mjs        Directory-pinned recovery subprocess
  core.mjs            Discovery, metadata, sharing, editing, removal, settings
  index.html          Library, Agents, Workspaces, Activity, Help & FAQ
  app.js              Frontend state, navigation, forms, API requests
  styles.css          Application layout/styles
  tokens.css          Theme variables
  base.css            Base styling
  icon.svg            App icon
  test/app.test.mjs   Isolated filesystem and HTTP regression checks
  scripts/package.mjs Build distributable apps with checked runtime downloads
  README.md           Setup and operational documentation

~/.config/skills-viewer/
  settings.json       Agent/workspace registry, history, pending recovery
  trash/<id>/skill    Archived skill directory or symbolic link
```

A repository skill example:

```text
my-project/.github/skills/log-triage/
  SKILL.md
  scripts/            Optional
  references/         Optional
```

**Link to source** creates a symbolic link such as `~/.copilot/skills/log-triage` pointing to that directory. The source and destination read the same underlying files; no periodic sync occurs. The original source must stay available, and the receiving agent must support that location and symlinks.

## Privacy and footprint

Uses Node's HTTP/filesystem modules and plain HTML/CSS/JavaScript with local system fonts. No package dependencies or external network requests at runtime. There is no polling: use **Rescan** after external changes. The footer reports server process RSS, not browser memory.

The server binds only to `127.0.0.1`. It checks Host/Origin, rejects cross-site requests, requires a per-process secret on every API read/write, and serves only an explicit static asset list. No login token is returned by inventory or embedded in public HTML. Skill documents are opened without following a symlinked SKILL.md, read with a fixed size bound, and displayed as escaped text.

Do not expose the server through a network proxy or run it as root. An attacker already running code as your user can read your files and is outside this app's isolation boundary. Skill scripts are never executed by the dashboard; review instructions before allowing agents to run them.

Settings, the last 200 activity events, and unexpired recovery records are stored atomically in `~/.config/skills-viewer/settings.json`. The directory/file are created only after a configuration change, share, or removal. To isolate data for another profile or testing:

```sh
SKILLS_VIEWER_DATA_DIR=/absolute/path/to/profile npm start
```

Plugin-managed, vendor-specific, disabled, or non-`SKILL.md` instruction formats are not automatically imported. Register a plugin's skills folder explicitly if it follows the directory convention. Custom paths provide file-level integration, not a guarantee of agent compatibility.

The app does not export registered skills when its source is published. Default profile data lives outside the checkout. Keep custom profiles outside the checkout too; `.gitignore` also excludes `settings.json`, `trash/`, `.env` files, and local design metadata. Inspect staged files before publishing.

## Publishing a private repository

From a committed application checkout with GitHub CLI installed:

```sh
gh auth login --hostname github.com --git-protocol https --web
gh repo create skills-viewer --private --source=. --remote=origin --push
gh repo view --json url,visibility
```

Authorize with the GitHub account that should own the repository. Confirm visibility is `PRIVATE`. If that account already has a `skills-viewer` repository or `origin` is already configured, stop and inspect it instead of overwriting its settings or force-pushing.

After committing updates, use `git push`. To publish version 1.0 artifacts after the private repo exists:

```sh
gh release create v1.0.0 dist/*.zip dist/*.tar.gz dist/SHA256SUMS.txt \
  --title "Skills Viewer 1.0" --notes "Local macOS and Linux apps. Unsigned macOS builds; see README for platform requirements."
```
